# 협력사 로그인 · 권한 (2026-10-29 분석 · 결정)

협력사(그룹웨어 계정 없음)도 DY ONE에 로그인해 배정된 프로젝트를 보고 일지를 올린다. 권한은 직원보다 낮게, 그러나 배제하지 않는다.
1~3단계 로컬 구현(2026-10-30, 6장). 4단계(배정·일지)부터는 아직이다.

## 2. 지금 DY ONE에서 막히는 점

1. 로그인 = 그룹웨어 로그인 API 확인 → `org.employee.login_id`에 있어야 통과(`AuthModule`). 협력사는 둘 다 없다.
2. `org.employee`는 SmartLab·SRS와 같이 쓰고, OrgSync가 그룹웨어 사용자가 아닌 사람을 비활성 처리 → 협력사를 넣지 않는다.
3. `project.project_member.employee_id`가 `org.employee` FK → 협력사를 배정할 수 없다.
4. **API 대부분이 `RequireAuthorization()`만** 건다 = 로그인만 하면 전 프로젝트·조직도·홈 집계·사양서·연계 앱이 보인다. 협력사를 받기 전에 "기본 차단 + 배정 프로젝트만"이 먼저 있어야 한다.
5. 운영 주소가 사내(192.168.30.111) → 현장 협력사가 쓰려면 외부 https 또는 VPN.

## 3. 결정

### 3-1. 명단: 주소록을 매일 미러(조회 전용)
- Worker `PartnerSyncJob`(OrgSync와 같은 방식): 공용 주소록 15의 그룹 → `partner.company`(id = 그룹 id), 연락처 → `partner.person`(id = 연락처 id, 이메일·부서·직위·회사).
- 주소록에서 빠지거나 다른 그룹으로 옮기면 person 비활성/회사 변경 → 로그인 즉시 정지. 협력사 퇴사 처리는 주소록 한 곳에서 끝난다.
- 우리 직원 메일(doolim-yaskawa.com)·그룹웨어 계정과 겹치는 연락처는 제외.

### 3-2. 로그인: 아이디 = 주소록 이메일, 비밀번호 = **회사별 공용 비밀번호**(변경 강제 없음)
사용자 결정(2026-10-29): 사람별 허용·발급 단계 없이, 회사별 공용 비밀번호를 계속 쓴다.

- 로그인 화면은 하나. 아이디가 `partner.person` 이메일이면 그 회사의 공용 비밀번호로 확인, 아니면 기존 그룹웨어 확인.
- 공용 비밀번호는 관리자 화면에서 회사별로 설정. **해시만 저장**(저장소·설정 파일·로그에 원문 없음).
- 같이 거는 장치(공용 비밀번호의 약점을 줄이는 것, 사용자 편의는 그대로):
  - **배정된 진행 프로젝트가 1개 이상인 사람만 로그인** — 배정이 곧 허용. 배정 안 된 사람은 비밀번호를 알아도 못 들어온다.
  - 주소록에서 빠지면 즉시 정지.
  - 회사 단위 '로그인 중지' 스위치 + 공용 비밀번호 교체(협력사 쪽 인원 이탈 때, 정기적으로는 분기 권장). 교체하면 그 회사 전원이 새 값으로.
  - 계정·IP별 실패 횟수 제한(기존 login rate limit 위에), 협력사 토큰은 직원보다 짧게(예: 8시간).
- 받아들인 위험(기록): 이메일은 짐작하기 쉬워 공용 비밀번호가 새면 그 회사 누구로든 로그인될 수 있다. 감사 로그·일지 작성자는 "그 계정으로 했다"일 뿐 본인 증명은 아니다. 한 사람만 막으려면 주소록에서 빼거나 배정을 해제한다.
- 나중에 올릴 수 있는 것: 메일 일회용 코드(2차 인증) — 모두 이메일이 있어 붙이기 쉽다.
- **초기값(사용자 결정 2026-10-30)**: 처음에는 5개 회사(71·72·439·450·640) 모두 **같은 공용 비밀번호 하나**로 시작한다. 회사별로 다르게 나누는 것·교체 주기는 나중에 정한다.
  - 값은 사용자에게 받았고, 이 문서·저장소·시드 SQL·설정 파일에는 쓰지 않는다. 구현할 때 관리자 화면(또는 로컬은 user-secrets)으로 넣고 DB에는 해시만 남긴다.
  - 구조는 회사별 해시 칸 그대로 둔다 → 나중에 회사별로 나눌 때 값만 바꾸면 된다.
  - 같은 값을 5개 회사가 같이 쓰므로, 한 곳에서 새면 5개 회사 전원에 영향이 간다(받아들인 위험에 추가).

### 3-3. 데이터(만들기 전 승인 필요)
- `partner.company`(+ 공용 비밀번호 해시·교체일·로그인 중지), `partner.person` — company·person은 Worker 미러, 비밀번호·중지는 관리자 화면이 씀.
- 배정: `project.project_member`에 `partner_person_id` 추가 + `employee_id` nullable + "둘 중 하나" check. role `pm`·`member` 그대로 → 협력사 PM도 같은 표.
- CLAUDE.md "쓰기 대상"에 `partner.*`·`project.project_member`를 추가해야 한다.

### 3-4. 권한(우리보다 낮게, 배제하지 않게)
토큰에 `kind=partner` + 역할 `partner`(부서 자동 부여 P2의 access.role 대분류). 협력사 토큰은 **허용 목록 API만** 통과(기본 차단), 프로젝트 하위 API는 배정 여부를 공통 필터로 확인.

| 기능 | 직원 | 협력사 member | 협력사 PM(드묾) |
|---|---|---|---|
| 프로젝트 목록 | 전체 | 배정된 것만 | 배정된 것만 |
| 기본정보·단계 보기 | ✅ | ✅ (고객 금액·ERP 금액 숨김) | ✅ |
| 일지·사진 업로드 | ✅ | ✅ | ✅ |
| 문서 내려받기 | 전체 | '협력사 공개' 파일 + 자기 회사가 올린 것 | 같음 |
| 단계·일정 편집 | 담당 | ❌ | ✅ 그 프로젝트만 |
| 인원 배정 | PM·관리자 | ❌ | 자기 회사 인원만 |
| 조직도·홈 집계·사양서 분석·AI·연계 앱·알림 설정 | ✅ | ❌ | ❌ |

- 주소록 부서(어플·제어·모듈러·설계·PM)는 세부 역할의 '연결 후보'로만 쓴다(자유 텍스트라 자동 확정 안 함).

### 3-5. 일지
- 프로젝트 문서에 `partner_log`(협력사 일지) 분류 + `visibility`(internal/partner).
- 296 업무일지 칸에 맞춤: 날짜, 투입 M/D, 업무내용(티칭·주말티칭대응·이벤트대응·양산대응·안전회의), 첨부 → 어느 회사가 일했는지 남는다.

## 6. 구현 현황 (1~3단계, 2026-10-30 로컬)

| 단계 | 들어간 것 | 코드 |
|---|---|---|
| 1. API 기본 차단 + 배정 필터 | Default·Fallback 정책 = 직원 전용, 토큰 `kind`, `.PartnerAllowed()`(허용 + 배정 확인, 미배정 404), 시작 시 허용 목록 검사 | `Platform/ProjectAccess.cs`·`CurrentUser.cs`, 각 모듈 |
| 2. partner 스키마 + 미러 | `partner.company`·`partner.person`, `project_member.partner_person_id`, Worker `partner-sync`(매일 08:10) | `server/db/partner.sql`, `Jobs/PartnerSyncJob.cs` |
| 3. 공용 비밀번호 + 로그인 분기 | 이메일이면 협력사 확인 → 회사 공용 비밀번호(해시) → 배정 1건 이상이어야 로그인. 관리자 화면 `/admin/partners` | `Modules/Partners/PartnersModule.cs`, `AuthModule.cs`, `web/src/pages/PartnersAdminPage.tsx` |

설계와 달라진 점(이유):
- **협력사 쓰기는 모두 4단계로 미룸**: 파일 올리기·고치기, 단계 변경(협력사 PM), 인원 배정. 지금 쓰기 API는 올린 사람·바꾼 사람을 직원 id로 남겨서, 협력사 id를 넣으면 잘못된 기록이 된다. 그래서 1단계 허용 목록은 보기 9개뿐이다(`ProjectAccess.PartnerAllowList`).
- 토큰 만료: 협력사 240분(직원 480분). 문서의 "예: 8시간"은 직원과 같아서 더 짧게 했다(`Auth:PartnerTokenMinutes`).
- '진행 프로젝트' = `project.project.is_active`. 협력사 목록은 직원 목록의 '진행 중 모집단'(영업중·수주·단계 있음) 조건 없이 배정된 것 전부를 보인다.
- 계정별 실패 제한: 5회 실패 → 15분 잠금. API 메모리에 두므로 재시작하면 풀린다.
- 웹: 협력사는 메뉴가 '프로젝트'만, 상세는 보기 전용(진행 상황 변경·단계 업무 기능·자료 올리기·인원 편집 숨김), 알림·화면 메모 없음.

로컬 검증(2026-10-30, 시험 API):
- 미러 133명. 회사별로 디와이로보틱스 77, 두림에프에이 19, 디와이플랜트 17, 대상이엔지 14, 디와이오토메이션 6명이다. 구매처는 0명이고, 이메일이 없는 1명과 우리 직원 1명은 뺐다. 이메일 중복은 0이다.
- 협력사 토큰으로 확인한 결과:
  - 허용한 9개 API는 200
  - 배정 안 된 프로젝트는 404
  - 직원 전용 API(홈·조직도·연계 앱 토큰 3개·사양서·시험 데이터·WORKS·모듈라·알림·허브·AI·MotoSim·식단·협력사 관리)는 403
  - 쓰기 API는 403
  - 프로젝트 목록과 찾기 결과에는 배정된 1건만 나온다
- 로그인 막힘은 상황마다 다르게 나온다.
  - 배정이 없으면 403
  - 비밀번호가 틀리면 401
  - 5회 넘게 틀리면 429
  - 회사 로그인 중지면 로그인은 403이고, 이미 받은 토큰도 401
- 직원 쪽은 그대로다.
  - kind 없는 옛 토큰도 그대로 통과한다.
  - 프로젝트 목록 건수는 기존 API와 같다(1943).
  - 협력사 행이 섞인 프로젝트의 인원 보기도 정상이다.
