# API 기본 차단 · 배정 필터 설계 (2026-10-30)

> 2026-10-30 로컬 구현함. 차이: 협력사 쓰기(파일 올리기·단계 변경·인원 배정)는 4단계로 미뤄 허용 목록은 보기 9개 — [README 6장](README.md#6-구현-현황-13단계-2026-10-30-로컬).

협력사 기능 [순서 1단계](README.md#4-순서제안). 협력사 계정이 생기기 **전에** 먼저 넣는다.
목표: 협력사 토큰은 "허용 목록에 있는 API + 배정된 프로젝트"만 통과하고, 새로 만드는 API는 따로 신경 쓰지 않아도 직원 전용이 된다.
이 단계에는 DB 변경이 없다(배정 확인 쿼리는 2단계 `partner_person_id`가 생긴 뒤 실제로 동작).

## 1. 지금 상태 (코드 확인, 2026-10-30)

- `Program.cs`: `FallbackPolicy = RequireAuthenticatedUser` → 로그인만 하면 모든 API 통과. 기본 정책(`DefaultPolicy`)도 같은 값.
- 모듈별로 그룹에 `.RequireAuthorization()`(인자 없음 = 기본 정책)을 건 곳과 안 건 곳이 섞여 있다. 둘 다 결과는 "로그인만".
- 역할 검사는 관리자 확인 두 곳뿐(`SpecDraftModule.IsAdminAsync` — 설비 이력·사양서 라이브러리 다시 읽기). 그 밖의 단계 변경·인원 배정·파일 삭제는 **직원이면 누구나** 할 수 있다(이번 범위 아님, 6장).
- JWT 클레임: `NameIdentifier`(=employee id), `Name`, `Role`, `login_id`. 직원/협력사를 나누는 값이 없다.
- `ProjectDto`에는 금액 칸이 없다 → README 3-4의 "고객 금액·ERP 금액 숨김"은 지금 숨길 것이 없음(금액이 추가되면 그때 협력사용 DTO에서 뺀다).

## 2. 구조

### 2-1. 토큰에 `kind` 클레임
- `kind = staff | partner`. 직원 로그인은 `staff`, 협력사 로그인(3단계)은 `partner`.
- 클레임이 없는 기존 토큰은 `staff`로 본다 → 배포해도 로그인된 직원이 쫓겨나지 않는다.
- 협력사 토큰의 `NameIdentifier` = `partner.person.id`, 추가로 `partner_company`(회사 그룹 id).
- `CurrentUser`에 `Kind`, `IsPartner` 추가.

### 2-2. 정책 두 개 — "기본이 직원 전용"
| 정책 | 조건 | 어디에 |
|---|---|---|
| `staff` | 로그인 + `kind != partner` | **DefaultPolicy와 FallbackPolicy 둘 다** |
| `project-member-or-staff` | 로그인(둘 다) | 허용 목록 엔드포인트에만 명시 |

- 두 기본 정책을 모두 `staff`로 바꾸면, 인자 없는 `.RequireAuthorization()`과 아무것도 안 건 엔드포인트가 전부 직원 전용이 된다 = 기본 차단.
- **주의(ASP.NET 동작)**: 그룹 정책과 엔드포인트 정책은 AND로 합쳐진다. 그룹에 `.RequireAuthorization()`(=staff)이 걸려 있으면 그 안의 엔드포인트에 협력사 정책을 붙여도 통과하지 못한다.
  → 허용 엔드포인트가 들어 있는 그룹(`ProjectFilesModule`, `OrgModule`의 `/api` 그룹)은 그룹 수준 `.RequireAuthorization()`을 지우고, 직원 전용 엔드포인트는 Fallback이 막게 둔다.
- SignalR 허브(`/hubs/notifications`)도 Fallback = staff로 막힌다. 협력사 알림은 4단계에서 따로 정한다.

### 2-3. 배정 필터 — 프로젝트 하위 API 공통
- 엔드포인트 필터 `ProjectScopeFilter`: 라우트 값 `id` 또는 `projectId`를 읽는다.
  - `staff` → 그냥 통과(직원은 지금처럼 전체).
  - `partner` → `project.project_member`에 (프로젝트, partner_person_id, is_active) 행이 있고 프로젝트가 진행 중인지 확인. 없으면 **404**(403이 아니라, 있는지조차 드러내지 않음).
- 목록형 API는 필터가 아니라 쿼리에서 거른다: 서비스 `ProjectScope.VisibleIdsAsync(user)` → 직원은 `null`(전체), 협력사는 배정된 id 집합.
  - 적용 대상: `GET /api/projects`, `GET /api/projects/lookup`.
- 허용 엔드포인트는 확장 메서드 하나로 묶는다: `.PartnerAllowed()` = `RequireAuthorization("project-member-or-staff")` + `AddEndpointFilter<ProjectScopeFilter>()`.
  → 정책만 붙이고 배정 확인을 빠뜨리는 실수를 막는다.
- 2단계 전(`partner_person_id` 없음)에는 협력사 토큰 자체가 발급되지 않으므로 필터의 협력사 경로는 쓰이지 않는다. 쿼리는 그때 연결한다.

### 2-4. 협력사 PM 판단
- 같은 필터가 배정 행의 `role`(pm/member)을 `HttpContext.Items`에 넣는다. 편집 API는 `RequirePartnerPm()` 필터를 하나 더 건다(직원은 통과, 협력사는 role=pm일 때만).

## 5. 검증

- **엔드포인트 목록 검사**: 개발 환경 시작 시(또는 테스트) `EndpointDataSource`의 모든 엔드포인트를 돌며 "staff가 아닌 정책을 가진 것"을 뽑아 3장의 허용 목록과 정확히 같은지 확인. 다르면 시작 로그에 경고 → 누가 실수로 협력사에 연 API를 바로 알 수 있다.
- **토큰 시험**(로컬만): 로컬 서명키로 `kind=partner` 시험 토큰을 만들어
  - 직원 전용 API(예: `/api/home/summary`, `/api/integrations/smartlab/token`, `/api/org`) → 403
  - 배정 안 된 프로젝트 `/api/projects/{id}` → 404, `/api/projects` → 빈 목록
  - 기존 직원 로그인·화면 동작은 그대로(클레임 없는 옛 토큰 포함).
- 시험 토큰·키는 저장소에 넣지 않는다.

## 6. 이번 범위 밖 (발견만 기록)

- 직원끼리의 권한: 단계 변경·인원 배정·파일 삭제를 지금은 직원 누구나 할 수 있다. 부서 자동 부여(P2 access.role) 뒤에 정하는 것이 맞다.
- `GET /api/projects/{id}/members`가 우리 직원 휴대폰·직통번호를 준다 → 협력사에게 보일지 4단계에서 결정.
