# 팀 제안 「사양서 부서별 검토와 개정본 관리」 ↔ 사양 판 흐름 설계 비교 (2026-10-30)

- 비교 대상
  - 팀 제안: 영업 김상우, 2026-10-29. 기준 코드는 DYONE_I `main` 0e06ffc.
  - 우리 설계: [사양 판 흐름 설계](사양%20판%20흐름%20설계%20(2026-10-30).md)와 [시안](사양%20판%20흐름%20시안.html).
- 제안서가 말한 지금 코드 상태는 맞는지 확인했다.
  - `SpecDeptReview.tsx`는 확인 상태 5가지와 의견을 **브라우저 localStorage에만** 저장한다. 주석에 "표 설계는 사용자 확인 뒤"라고 적혀 있다.
  - `DeptMatcher.cs`가 있다.

## 1. 공통점
- 사양서를 올리면 초안과 부서별 확인을 만든다. 그다음 **관련 부서에만** 알리고, 부서가 확인하면 영업이 모아 본다.
- 사양서 차수(판)를 하나로 묶는다. 이전 판과 비교해서 **바뀐 것만, 걸리는 부서만** 다시 보게 한다.
- AI·규칙은 제안만 하고 확정은 사람이 한다. 보낼 부서는 영업이 더하거나 뺄 수 있다.
- 보낼 때 변경 사유를 한 줄 적는다. 회신 기한을 두고, 미확인 부서에는 다시 알린다.
- 누가·언제·몇 차 판을 확인했는지 남긴다.

| 첫 순서 | 확인 결과 서버 저장·공유 | 읽기 정확도(로봇 용도·취소선) |

## 3. 묶으면 좋은 점
1. **두 줄로 역할을 나누면 서로 빈 곳이 채워진다.**
   - 사양서 판 → 팀 제안처럼 *부서별 확인 항목* 단위로 검토하고 이어받는다.
   - 사양정리 판 → 우리 설계처럼 *칸* 단위로 비교하고 알린다.
   - 판 줄기 하나에 두 줄을 같이 그린다.
2. **"무엇이 바뀌었나"와 "누가 다시 볼까"를 잇는다.**
   - 바뀐 것 찾기: 핵심 항목 14개 + 그 밖의 변경 목록
   - 다시 볼 부서 정하기: 바뀐 문장이 걸리는 `역할.항목`
   - 항목 키(`design.mount`)와 칸 키(`Robot`)는 판이 바뀌어도 이름이 같다. 그래서 둘 다 이어받기 기준으로 쓸 수 있다.
3. **검토 중에 새 판이 오는 경우는 팀 제안 규칙을 그대로 가져온다.** 시안에는 이 경우가 없다.
   - 하던 검토는 이어 간다.
   - 시작 전이면 새 판만 본다.
   - 바뀐 항목만 OK를 풀고, 나머지 OK는 "이어받음"으로 표시한다.
4. **서버 저장 표를 처음 만들 때 판 정보를 넣는다**(팀 제안 7장). 판 묶음, 기준 판 번호, 이어받음 여부가 처음부터 있어야 나중에 판 비교를 붙이기 쉽다. 우리 설계의 "파일 저장"보다 이쪽이 맞다. 여러 사람이 현황판을 같이 봐야 하기 때문이다.
5. **현황판은 하나로 만든다.** 우리 시안의 판 × 부서 표를 위에 두고, 칸을 누르면 팀 제안의 항목별 상태가 열린다.
6. **우리 설계에만 있는 것은 그대로 덧붙인다.** 팀 제안에 없는 가치다.
   - 사양서 ↔ 사양정리 불일치 경고
   - 이전 사양정리 이어받기
7. **팀 제안에만 있는 것은 설계에 추가한다.**
   - 열람 권한(검토 요청 받은 팀에 그 사양서만 공개)
   - 회신 기한

## 4. 묶으면 안 되는 점 · 조심할 점
1. **사양서 OK와 사양정리 확인을 한 상태로 섞으면 안 된다.**
   - 사양서 OK는 "고객 요구를 봤다"는 뜻이고, 사양정리 확인은 "우리 견적용 정리 값을 봤다"는 뜻이다.
   - 기록도 현황판 줄도 따로 둔다.
2. **"모든 팀 OK = 차수 확정"은 사양서에만 쓴다.** 사양정리는 수주 뒤에도 계속 바뀐다(아산 rev1~rev7). 그래서 '확정' 개념을 붙이면 맞지 않는다.
3. **항목 이어받기에는 빈틈이 있다.**
   - 부서별 확인 항목은 키워드로 찾는다. 그래서 바뀐 문장이 어느 항목 키워드에도 안 걸리면 "변경 없음"으로 OK가 그대로 이어진다.
   - 예: 아산 V5의 "플립도어", "HMI 퍼지모드" 같은 새 요구
   - 보완 방법
     - 핵심 항목 비교와 "그 밖의 변경 n건" 목록을 같이 보여 준다.
     - 어느 항목에도 안 걸린 변경은 영업이 부서를 직접 고르게 한다.
4. **질문·의견 기능은 범위를 먼저 정해야 한다.**
   - 팀 제안의 "고객 질의 필요·내부 결정 필요·의견"은 사실상 질문 기능이다.
   - 10-30에 시안에서 부서 질문을 뺐으므로, 상태를 몇 개로 둘지 사용자가 정해야 한다.
   - 추천: 처음엔 `확인 / 해당 없음 / 재검토 필요` 정도로 줄이고, 의견은 나중에 붙인다.
5. **(4-1에서 바뀜 — 아래는 처음 생각) 보내는 시점 규칙은 문서마다 다르게 둔다.**
   - 사양서는 "확정 차수만 보낸다"(팀 제안)가 맞다. 협의 중인 초안까지 보내면 부서가 지친다.
   - 사양정리는 영업이 저장할 때 보낼지 고른다(우리 설계).
6. **팀 전용 AI는 마지막에 한다.** 사내 AI 키가 아직 없다(`Llm:ApiKey` 없음, 규칙 초안으로 동작). 대외비 사양서(254건 중 66건)는 외부 AI로 보내면 안 된다.
7. **읽기가 틀리면 둘 다 틀린다.**
   - 광주1 S.C.O 판은 취소선 옛 값("~~11대~~ 7대") 때문에 항목 비교도 칸 비교도 틀린 값으로 "바뀜/그대로"를 판단할 수 있다.
   - 로봇 용도(에어블로우 등)가 빠진 것도 마찬가지다.
   - 서버 저장보다 먼저이거나 적어도 같이 고쳐야 한다.
8. **저장 표는 쓰기 허용 범위 밖이다.** 지금 쓰기 대상은 `org.*`·`project.project`·`sync.*`뿐이다. 확인 결과 표를 새로 만들려면 사용자 승인과 DEPLOY 문서 갱신이 필요하다.

## 4-1. 정한 것 (2026-10-30 사용자와 정리)
- **'고객 확정 차수 / 협의 중' 구분은 뺐다.**
  - 이유 1: 파일 이름에 확정 표시가 없어서(아산 V2·V4·V5) 영업이 매번 감으로 골라야 한다.
  - 이유 2: 나눈 목적은 "같은 검토를 여러 번 하지 않게"였는데, 바뀐 항목만 다시 보내고 나머지는 이어받으므로 이미 해결된다. 아산 V4→V5는 한 줄뿐이었다.
- 대신 사양서 판을 올릴 때도 사양정리처럼 **보낼지 영업이 고른다**("알리지 않고 올리기").
- **팀 OK가 다 나지 않아도 아무것도 막지 않는다.**
  - 모든 팀 OK는 그 판에 붙는 '확정' 결과 표시일 뿐이다.
  - pptx 내려받기·단계 변경 때 "미확인 n건" 경고를 띄우고, 확인 안 된 채 진행한 기록을 남긴다.
  - 이유: 견적 기한은 고객이 정한다.

## 6. 제안자에게 답할 것 (팀 제안 9장 질문)
- **차수 개념을 표에 넣을 수 있는가**: 넣을 수 있고, 넣는 게 맞다. 사양정리 판도 같은 표 구조로 다룰 수 있게 한다.
- **역할 ↔ 부서 연결**: 조직도 동기화(`org.department`) + dept-auto-assign 설계의 역할 키를 쓴다. 지금 `org.role_mapping`은 0건이다.
- **2차를 같은 묶음으로 인식하는 방법**: 파일 이름으로 추정하고, 업로드할 때 영업이 확인하게 한다(시안 8단계).
- **사내 AI 연결 일정**: 키가 아직 없다. 일정은 별도로 정해야 한다.
